# Paper Analysis Desk 与多宿主产品设计

**日期：** 2026-08-23  
**状态：** 已确认  
**范围：** 工作台视觉与交互、两套旗舰演示案例、Codex / DeepSeek Harness / WorkBuddy 多宿主交付。

## 1. 产品定义

Data2Doc2Data 是一个本地优先的业务分析任务工作台，而不是以聊天为主体的通用 Agent。产品由一套确定性分析引擎支撑，提供两种入口：

1. 本地 Web 工作台：导入数据和文档，查看 Dashboard、证据链、假设图、运行过程与可下载报告。
2. Agent 原生工具：通过 MCP 和宿主说明在 Codex、DeepSeek Harness、腾讯 WorkBuddy / CodeBuddy 中调用同一套能力。

原始数据默认在本地计算。发送给模型的内容只包含任务所需的聚合结果、有界样例和相关文档片段。确定性结论、证据引用和审批记录由本地主机保存。

## 2. 视觉方向：Paper Analysis Desk

采用 Paper Neo-Brutalism 的纸张、工程网格、硬边框和编辑感，但不复制参考页面的内容或品牌资产。

### 2.1 设计令牌

- 页面底色：`#f4f1e8`
- 纸张面板：`#fffdf7` / `#fbfaf5`
- 主墨色：`#151511`
- 次级文字：`#6f6b60`
- 品牌高亮：`#08d36c`
- 强边线：`#171713`
- 弱分隔线：`#ded8ca`
- 圆角：默认 2px，仅表单控件允许 4px
- 阴影：4px 黑色硬阴影，只用于选中态、主操作和可拖拽产物
- 背景：32px 工程网格
- 字体：DM Sans 加系统中文无衬线回退；报告标题可使用编辑感更强的衬线回退

### 2.2 工作台结构

- 顶部黑色状态条：当前案例、运行状态、数据更新时间、导出入口。
- 左侧“案例目录”：任务、数据集、文档、规则、历史运行。
- 中间“分析纸面”：总览、数据、文本、证据、假设、历史六个视图。
- 右侧“分析员批注”：AI 对话、分析计划、工具调用、待审批操作。
- 底部可展开执行轨道：按真实运行事件展示计算、抽取、验证和证据连接。

主画布始终占据视觉中心。右侧助手可收起；移动端按“分析 / 过程 / 助手”切换，不强行保留三栏。

### 2.3 语义与动效

- 绿色：已验证；黄色：待验证；红色：冲突；灰色：证据不足。
- 荧光绿只承担品牌和主操作，不替代全部状态色。
- 运行事件使用纸条滑入、编号盖章、高亮扫过和证据连线生长表达。
- 动画必须由结构化事件驱动，不能伪装模型正在执行。
- `prefers-reduced-motion` 下关闭位移和连续动画，直接呈现最终状态。
- 报告使用同一纸张语言，并具备打印样式与单文件 HTML 导出。

## 3. 两套旗舰演示案例

现有三个小型案例保留为边界条件与回归测试夹具。产品入口只突出以下两套完整案例，全部明确标注为合成数据且不包含个人信息。

### 3.1 B2B SaaS：增长提速、留存承压

- 26 周、8 个核心指标，至少 208 条周度指标记录。
- 指标：MRR、试用数、激活率、8 周留存率、客户流失率、扩张收入、CAC、支持工单积压。
- 文档：年度增长策略、定价实验记录、客户研究摘要、KPI 口径字典。
- 分析主线：获客上升是否被激活和留存下降抵消；定价实验是否造成不同客群的相反结果。

### 3.2 全渠道零售：大促增收、利润与履约恶化

- 26 周、10 个核心指标，至少 260 条周度指标记录。
- 指标：GMV、订单量、转化率、客单价、毛利率、退款率、退货率、延迟交付率、缺货率、复购率。
- 文档：大促计划、商品策略、履约事故记录、财务复盘、指标口径字典。
- 分析主线：GMV 增长是否建立在折扣和低毛利上；库存与履约问题是否引发退款和复购下降。

### 3.3 案例包契约

```text
case.json
metrics.csv
documents/*.md
rules.json
hypotheses.json
expected.json
```

- `case.json`：案例元数据、业务问题、时间范围、入口文案。
- `metrics.csv`：可直接导入的长表指标数据。
- `documents/`：可检索、可引用的文本材料。
- `rules.json`：确定性业务规则。
- `hypotheses.json`：建议调查路径，不作为预设结论。
- `expected.json`：测试用黄金结果、最低证据数量和关键引用。

入门页提供“示例案例库”。一键加载后创建隔离任务、附加数据与文档、导入规则并运行基础画像；用户仍可查看每一步产物。

## 4. 多宿主交付

### 4.1 统一运行时

- `data2doc2data setup` 启动本地工作台。
- `data2doc2data mcp` 启动 stdio MCP 服务。
- `data2doc2data doctor` 只读检查本地引擎、案例包、MCP 工具和宿主配置，不静默修改用户配置。

### 4.2 集成目录

```text
integrations/
  codex/
  deepseek-harness/
  codebuddy/
```

每个目录包含经过验证的配置模板、安装说明、可用工具和卸载方式。三个宿主调用相同的 `source_profile`、`analyze`、`check_rules` 工具，不复制分析实现。

### 4.3 验证

- 案例包 schema、记录数量、引用完整性和黄金结果测试。
- MCP stdio 协议契约测试。
- Codex、DeepSeek Harness、CodeBuddy 配置模板解析与启动测试。
- 桌面与 390px 工作台视觉回归。
- 两套案例各完成一次从加载到 HTML 报告导出的端到端测试。

## 5. 交付顺序

1. 建立视觉基线与工作台设计系统。
2. 生成并验证两套完整案例包。
3. 改造入门页、任务壳层、Dashboard、过程轨道和报告。
4. 增加多宿主集成模板与诊断命令。
5. 完成单元、契约、端到端和三轮使用测试。
